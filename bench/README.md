# 소비전류 계측 (PWR_BENCH)

차량 상시전원에 물린 진단기가 **DC-DC 입력단(12V 쪽)에서 150~200mA** 를 먹어 하루를 못 버틴다.
어디서 나가는지 모른 채 최적화하면 엉뚱한 데를 손대므로, 먼저 **바닥부터 쌓아 올리며** 세 지점을 잰다.

전제: **차키 명령은 즉시 수행돼야 한다.** 그래서 "MQTT 상시연결"은 끌 수 없는 요구사항이고,
이 계측의 목적은 그 요구를 지킬 때의 **소비전류 하한**을 확정하는 것이다.

---

## 세 가지 계측 상태

빌드 시 [`examples/KeyplusDiagnostic/config.h`](../examples/KeyplusDiagnostic/config.h) 의 `PWR_BENCH` 하나로 결정된다.
차키(GPIO)는 세 모드 모두 켜져 있다 — 소비가 사실상 0 이고, 최적화 후에도 남아야 하는 유일한 기능이라 기준선에 포함시킨다.

| 파일 | `PWR_BENCH` | 상태 | 무엇이 켜져 있나 |
|---|---|---|---|
| `bench-3-floor.bin` | 3 | **floor** | ESP32 + 보드 정지전류. 모뎀은 PWRKEY 펄스 생략 → OFF |
| `bench-1-idle.bin` | 1 | **idle** | floor + 모뎀 전원인가·미등록(유휴) |
| `bench-2-mqtt.bin` | 2 | **mqtt** | idle + LTE 등록 + MQTT 상시연결 + 30초 telemetry 발행 |
| `bench-4-mqtt-gps.bin` | 4 | **mqtt+gps** | 2 + **GNSS 만** |
| `bench-5-mqtt-obd.bin` | 5 | **mqtt+obd** | 2 + **OBD2/CAN 만** |
| `bench-0-full.bin` | 0 | 정상 | 전체 기능(검산용) |

3·1·2 는 GPS·OBD2 가 모두 꺼져 있다. 4·5 는 그 위에 하나씩만 얹어 **따로 잰다** —
둘을 한꺼번에(0 − 2) 재면 합계만 알 뿐 어느 쪽을 손봐야 할지 모르기 때문이다.
상태LED·오프라인버퍼·고빈도샘플은 1~5 전부에서 꺼져 있다(0 만 켜짐).

전처리기로 조합을 확인했다(빌드 성공만으로는 토글이 의도대로 갈렸는지 알 수 없다):

| 모드 | FEATURE_GPS | FEATURE_OBD2 | FEATURE_LTE |
|---|---|---|---|
| 2 | 0 | 0 | 1 |
| 4 | **1** | 0 | 1 |
| 5 | 0 | **1** | 1 |
| 0 | 1 | 1 | 1 |

### 이번 측정(작업 4 준비) — GPS·OBD2 몫 확정

```
(4 − 2) = GNSS 상시 ON 비용      ← GNSS duty cycle 의 값어치
(5 − 2) = CAN 트랜시버 + TWAI 비용
검산: (4 − 2) + (5 − 2) ≈ (0 − 2)
```

기준선은 이미 측정돼 있다: **mqtt(2) = 80~100mA (평균 85 안팎)**.

| 모드 | 5분 평균 | 2 와의 차이 | 비고 |
|---|---|---|---|
| 2 mqtt | 85mA | — | 기준선(측정 완료) |
| 4 mqtt+gps | mA | mA | ← GNSS 몫 |
| 5 mqtt+obd | mA | mA | ← CAN 몫 |
| 0 정상 | mA | mA | 검산 |

**판정 기준**
- (4 − 2) ≥ 25mA → GNSS duty cycle(5분 주기) 구현할 값어치 충분
- (4 − 2) ≤ 10mA → GNSS 는 손댈 것 없음. 남은 건 모뎀 47mA 뿐이고 하드웨어 말고 수단이 없다
- (5 − 2) 가 크면 → CAN 트랜시버 전원 게이팅(하드웨어 필요) 검토 대상

⚠️ 모드 5(OBD2)는 **차량에 연결하지 않은 상태**에서 재면 링크 미확립 → `Obd2::end()` 가
TWAI 를 정지시킨 상태의 값이 나온다. 즉 **주차 중(시동 꺼짐) 실제 상황과 같은 조건**이라
이번 목적에는 오히려 맞다. 주행 중 값을 알고 싶으면 차량에 물린 채 따로 재야 한다.

차감으로 각 항목의 몫이 나온다:

```
floor            = ESP32 + 보드 (+ DC-DC 변환손실)
idle  − floor    = 모뎀 유휴 비용
mqtt  − idle     = LTE 등록 유지 + MQTT 상시연결 + 30초 발행 비용
```

정상 동작 펌웨어(`PWR_BENCH=0`)를 같은 조건에서 한 번 더 재면 `정상 − mqtt` 가 GPS+OBD2 몫이다.

## ⚠️ 플래시 전에 반드시 읽을 것

- **모드 1·3 은 LTE 가 꺼져 있어 OTA 로 되돌릴 수 없다.** 원복하려면 USB 물리 접속이 필수다.
  차량에 설치된 상태로 올리지 말고, 손이 닿는 책상 위에서만 계측한다.
- 모드 2 는 LTE·OTA 가 살아 있지만, telemetry 에 GPS·OBD 필드가 빠진 채 올라간다.
  운영 브로커에 붙이면 서버 쪽 데이터가 그 구간만 비게 되니 계측 시각을 남겨둘 것.
- 계측이 끝나면 `PWR_BENCH` 를 **반드시 `0` 으로 되돌린다.** 저장소 기본값은 0 이다.

## 측정 절차

### 측정 구성 — Nordic PPK2 소스미터 모드

PPK2 가 **5V 를 보드에 직접 공급하면서** 그 전류를 잰다. 차량용 12V→5V 컨버터는
경로에 없으므로, 여기서 나오는 값은 **펌웨어가 줄일 수 있는 몫 그대로**다.

```
PPK2 (5V 공급 + 전류측정) ──── 보드 5V 입력
```

⚠️ 이 구성으로는 **차량 배터리가 실제로 잃는 양을 알 수 없다.** 12V→5V 컨버터의
경부하 효율(싼 벅은 30~50%)과 자체 소비(5~20mA)가 통째로 빠져 있기 때문이다.
펌웨어 절전이 끝나면 실제 하네스를 물린 채 **12V 입력단에서 한 번 더 재야** 한다.
그때 5V 부하가 25mA 로 줄었는데 12V 쪽이 안 줄면, 남은 범인은 컨버터다.

### 각 상태별 절차

1. 해당 bin 을 플래시하고 부팅 배너에 `⚠️ PWR_BENCH: <n>` 이 찍히는지 확인한다.
   (이 줄이 없으면 정상 빌드가 올라간 것 — 계측값이 무효다)
2. 안정화 대기: floor·idle 은 1분, mqtt 는 **MQTT 접속 완료 후** 3분.
3. 평균 전류를 읽는다. floor·idle 은 5분, mqtt 는 **10분** 이상.
   → 모드 2 는 30초 발행마다 TX 스파이크가 있어 짧게 재면 우연히 스파이크를 피하거나 걸린다.
4. 모드 2 는 스파이크 최대값도 같이 적는다(피크 전류는 컨버터 용량·전압 sag 판단에 쓴다).

## 측정 결과 (2026-08-10)

계측기: **Nordic PPK2 (소스미터 모드, 5V 공급)**.
→ 보드의 5V 입력단에서 직접 재고 **공급한 값이다. 차량용 12V→5V 컨버터는 측정 경로에 없다.**
아래 수치는 전부 **5V 기준**이며, 차량 12V 쪽 실제 부하는 여기에 컨버터 효율을 나눠야 한다.

| 상태 | 5V 안정화 | 전력 | 비고 |
|---|---|---|---|
| floor (3) | **63mA** | 0.32W | 초반 120mA → 안정화 63mA |
| idle (1) | **110mA** | 0.55W | 초반 120mA |
| mqtt (2) | **120mA** | 0.60W | 피크 150mA (30초 발행 TX) |
| 정상 (0) | 150~200mA | 0.75~1.0W | GPS·OBD2 포함 기준선 |

차감:

```
floor            63mA  ← ESP32(240MHz 상시, 한 번도 안 잠) + 보드 정지전류
idle − floor     47mA  ← 모뎀 (전원인가 후 자동 망등록·유휴, 슬립 차단됨)
mqtt − idle      10mA  ← LTE 등록유지 + MQTT 상시연결 + 30초 발행
정상 − mqtt    30~80mA ← GPS 상시 + OBD2/CAN 트랜시버
```

## 해석 — 확정된 것

**1. MQTT 상시연결은 싸다 (10mA / 전체의 7%).**
"차키 명령 즉시 수행"이라는 요구는 소비전류의 원인이 **아니다**.
상시 TCP 를 포기하고 eDRX 페이징으로 가는 설계 변경은 **불필요하다** — 응답 지연을
5~10초 감수해서 얻을 게 10mA 뿐이다. 상시연결을 유지한 채 나머지를 줄이는 게 맞다.

**2. 진짜 범인은 두 개다 — floor 63mA 와 모뎀 유휴 47mA (합쳐 전체의 73%).**
둘 다 "아무 일도 안 하는 동안" 나가는 돈이다.

**3. 모뎀 유휴 47mA 는 슬립을 명시적으로 막아둔 결과다.**
`modemPowerOn()` 이 DTR 을 LOW 로 고정하고 `AT+CSCLK` 설정이 없다 —
A7670E 가 유휴 슬립에 들어갈 수 없는 상태로 박아둔 것이다.

**4. floor 63mA 는 거의 전부 ESP32 다.**
PPK2 가 5V 를 직접 공급하므로 컨버터 손실은 이 수치에 없다. 63mA 의 내역은
ESP32 240MHz 상시 활성 ~45mA + 보드 정지전류(LDO·전원LED·레벨시프터) ~15mA 로,
데이터시트 예상과 거의 정확히 일치한다. **줄일 여지가 크고, 방법도 정해져 있다(재우기).**

**5. ⚠️ 차량 12V 쪽 실제 부하는 아직 아무도 모른다.**
이 계측은 5V 입력단이라 차량용 12V→5V 컨버터가 통째로 빠져 있다.
그 컨버터의 경부하 효율과 자체 소비는 별도 측정이 필요하며,
5V 부하를 25mA 로 줄여도 컨버터 자체 소비가 15mA 면 이득이 반감된다.
→ **펌웨어 절전이 끝난 뒤 실제 하네스(12V 입력)에서 한 번 더 재야 한다.**

## 작업 1 — 모뎀 유휴 슬립 (`AT+CSCLK`) ❌ 효과 없음, 종료

**결론: 전류에 확연한 차이가 없어 `FEATURE_MODEM_SLEEP 0` 으로 껐다.**
코드는 남겨뒀다(계측 도구로 쓸모 있고, DTR 배선이 확인되면 mode 1 로 되살릴 수 있다).

| 시도 | 수면비율 | 깨움 | 전류 | 판정 |
|---|---|---|---|---|
| mode 1 (DTR) | 65% | 118회 (평균 4.1초) | 변화 없음 | ❌ 슬립 자체가 안 걸림 |
| mode 2 (RX) + quiet-idle | 86% | 15회 | **확연한 차이 없음** | ❌ 자도 baseline 이 안 줄음 |

**왜 안 됐나** — AT 매뉴얼 10.2.7 이 이 명령을 **"Control UART Sleep"** 으로 규정한 그대로다.
UART 를 재우는 것으로는 모듈 baseline 47mA 를 건드리지 못한다.
mode 1 이 아예 안 걸린 건 별개 문제로, GPIO25 가 모듈 DTR 핀에 닿아 있지 않아서다
(HW 매뉴얼 3.3.2: "CSCLK=1 에서 DTR 을 올리면 串口功能不能正常通讯" — 그런데 UART 가 살아 있었다).

**남은 자산**
- `msleep probe` — 기상 지연(ms)을 재서 "실제로 자는가"를 판정하는 계측 도구
- quiet-idle 로직 — 자는 동안 AT 프로브·전원표본을 거른다. 깨움 118 → 15회로 입증됨.
  light sleep 단계에서 그대로 재사용한다.
- **배운 것: 이 보드는 utilities.h 의 핀 정의가 실제 배선을 보장하지 않는다.**
  다음 단계에서 RI(GPIO33)에 의존하기 전에 **반드시 배선부터 확인할 것.**

## 작업 2 — ESP32 CPU 80MHz ✅ 성공 (−36mA)

| 조건 | floor(3) | mqtt(2) |
|---|---|---|
| 240MHz (기준선) | 63mA | 120mA |
| **80MHz** | **27mA** | 100~130mA (범위 — 평균 재측정 필요) |
| 차이 | **−36mA** | 확인 중 |

floor 63 → 27mA. 예상(−20mA)을 넘는 −36mA 로, **지금까지 시도 중 유일하게 확실히 성공한 항목**이다.
초기 10초간 80mA 는 부팅 전이(플래시/PSRAM 초기화 + OBD2 링크 재시도)이고 유지 구간은 27mA.

⚠️ mqtt(2)가 `100~130mA` 로 보고됐는데 이건 **평균이 아니라 순시값 범위**다.
차감 예측은 27(floor) + 47(모뎀) + 10(MQTT) = **84mA** 인데 관측 범위가 그보다 높다.
평균값을 다시 재서 예측과 맞는지 확인할 것 — 안 맞으면 80MHz 가 모뎀 쪽 동작에
영향을 준다는 뜻이라 따로 봐야 한다.

mqtt(2) 재측정 = **80~100mA**. 차감 예측 27(floor) + 47(모뎀) + 10(MQTT) = 84mA 와 일치한다.
→ 앞선 측정 모델이 맞다는 교차검증이다.

## 작업 3 — light sleep ❌ 하드웨어 배선 없이는 불가

| 항목 | 결과 |
|---|---|
| RI(GPIO33) 엣지 | **670초 동안 0회** (그 사이 telemetry 20회 + 차키 2회 = URC 20+회) |
| `wake sleep 20` 기상 원인 | TIMER (아무도 안 깨움), 기상 후 UART 대기 바이트 0 |
| 자는 동안 차키 명령 | **응답 없음** |

**RI 미배선 확정.** DTR(GPIO25)에 이어 두 번째다 —
**이 보드에서 utilities.h 의 핀 정의는 실제 배선을 보장하지 않는다.** TXD/RXD/PWRKEY/
RESET/POWERON 만 실제로 물려 있다고 보는 편이 안전하다.

**왜 UART 엣지 기상으로도 안 되는가** — 설령 기상이 걸려도 **기상 지연 동안의 바이트는
잃는다.** ESP32 light sleep 복귀는 대략 1ms 이고 115200bps 에서 1ms = **약 11바이트**다.
URC 앞의 `\r\n` 2바이트로는 못 막고 `+CMQTTRX` 헤더가 잘린다.
RI 가 유일한 답이었던 이유가 이것이다 — **URC 본문보다 60ms 앞서** 통지가 오기 때문이다.

**남은 선택지**
- 모듈 RI 패드에서 GPIO33 으로 점퍼(하드웨어 개조). bare 모듈이라 패드 접근성 확인 필요.
- 또는 RTS/CTS 하드웨어 흐름제어(`AT+IFC=2,2`) — 자기 전에 RTS 를 내려 모뎀이 送信을
  보류하게 한다. 이쪽이 유실이 원천적으로 없어 더 낫지만, **RTS/CTS 도 배선 확인이 먼저다**
  (DTR·RI 전례를 보면 안 되어 있을 가능성이 높다).
- 배선을 안 할 거라면 light sleep 은 접는다. floor 27mA 가 ESP32 쪽 바닥이다.

### (참고) floor 27mA 의 내역

남은 27mA 는 대략 ESP32 @80MHz 활성 20~25mA + 보드 정지전류(LDO·전원LED) 몇 mA 다.
클럭은 80MHz 가 바닥이므로(그 아래는 APB 가 따라 내려가 UART 파손) **다음 수단은 light sleep** 이다.
ESP32 light sleep 은 0.8mA 급이라 90% 를 자면 floor 가 5mA 대로 내려간다(−22mA).

⚠️ **선행 조건: 모뎀 URC 를 놓치지 않을 기상 경로.**
light sleep 중에는 APB 가 꺼져 UART 가 클럭을 못 받아 **들어오는 바이트가 유실된다.**
차키 명령(`+CMQTTRX*`)이 그 경로라 그냥 재우면 안 된다.
해법은 RI 핀(GPIO33)이다 — A7670 HW 매뉴얼 3.3.2 에 따르면 URC 를 올리기 전에
RI 가 **60ms LOW 펄스**를 내므로, 그 엣지로 깨우면 URC 본문을 온전히 받는다.
**단 DTR(GPIO25)이 배선돼 있지 않았던 전례가 있다 — RI 배선부터 실측 확인할 것.**

## (참고) 작업 2 기록 — CPU 클럭

floor 63mA 는 ESP32(240MHz 상시) + 보드 정지전류가 전부다. ESP32 는 클럭에 거의
비례해 먹으므로 240 → 80MHz 로 **20mA 안팎** 이 빠질 것으로 본다. 위험이 낮은 단계다.

⚠️ **80MHz 가 안전한 바닥이다.** 그 아래로 내리면 APB 가 CPU 를 따라 내려가 UART
보레이트가 전부 어긋난다(모뎀·콘솔 통신이 통째로 깨진다). `config.h` 에서 `#error` 로 막아뒀다.

부팅 배너에 `cpu : 80MHz` 가 찍힌다 — 계측 전 반드시 확인할 것.

| 조건 | floor(3) | mqtt(2) |
|---|---|---|
| 240MHz (기준선) | 63mA | 120mA |
| 80MHz | mA | mA |

## (참고) 작업 1 상세 — 모뎀 유휴 슬립 시도 기록

구현 완료. `bench-2-mqtt.bin` 에 포함돼 있고 **기본 활성**이다.
설계·위험은 [`modempwr.h`](../examples/KeyplusDiagnostic/modempwr.h) 참고.

**재플래싱 없이 A/B 비교가 된다.** PPK2 를 물린 채 콘솔에서:

```
msleep off      → 슬립 해제 (기존 동작 = 120mA 기준선)
msleep on       → 슬립 활성
msleep mode 1   → DTR 슬립 (모듈 DTR 핀 배선 필요)
msleep mode 2   → RX 슬립 (핀 불필요 — 시리얼 데이터로 기상)  ★ 현재 기본값
msleep probe    → 슬립이 실제로 걸리는지 모뎀 반응으로 판별
msleep          → 수면비율 / 누적수면 / 깨움횟수
```

### 1차 시도 결과 (2026-08-10 16:52~16:56) — 실패, 원인 규명됨

`CSCLK=1`(DTR 슬립)은 OK 를 받았고 수면비율 65% 까지 올라갔는데 **전류는 1mA 도 안 변했다.**
`msleep probe` 가 2회 모두 "재운뒤 AT=응답" 을 냈다.

A7670 하드웨어 설계 매뉴얼 3.3.2 원문:
> 当用户设置"AT+CSCLK=1"后，拉高DTR引脚，模块将自动进入休眠模式，**此时串口功能不能正常通讯**。

즉 "자면 UART 가 죽는다"가 제조사가 규정한 정상 동작이다. AT 가 응답했다 = **모듈이
잠들지 않았다** = **GPIO25 가 모듈 DTR 핀에 닿아 있지 않다.**

같이 드러난 두 번째 문제: 깨움 118회 / 누적수면 316초 = **평균 4.1초짜리 수면**.
AT 프로브(5초)와 전원표본(10초)이 유휴 창을 잘게 썰고 있었다.
⚠️ 단, 이 둘은 UART 로컬 명령이라 **무선(RRC)에는 영향이 없다.** 막고 있던 것은
UART 슬립뿐이다.

### 2차 시도 준비 (구현 완료)

두 가지를 고쳤다.

1. **`CSCLK=2`(RX 슬립)를 기본값으로** — DTR 핀이 필요 없다. 시리얼로 아무 데이터나
   보내면 깨어난다(AT 매뉴얼 10.2.7). 배선 문제를 통째로 우회한다.
2. **자는 동안 AT 프로브·전원표본을 거른다**(`MODEM_SLEEP_QUIET_IDLE`).
   → 깨움이 발행 주기(30초)에만 묶여 **25초 이상의 연속 유휴 창**이 생긴다.

`msleep` 의 **수면비율%** 이 계기판이다. 90% 를 넘는데도 전류가 안 떨어지면
이 모듈의 슬립이 baseline 을 못 줄이는 것이므로, **모뎀 슬립을 접고 ESP32 절전(floor
63mA)으로 넘어가는 판단 근거**가 된다.

### 주기 발행이 방해가 되지 않는 근거

"30초마다 메시지를 보내는데 모뎀이 쉴 수 있나"는 이미 1차 측정이 답했다:
`mqtt(120) − idle(110) = 10mA`. **주기 발행이 얹는 비용은 10mA 뿐**이고,
나머지 47mA 는 발행과 무관한 모듈 상시 소비다. 슬립이 겨냥하는 건 그 47mA 다.

### 합격 조건 — 전류만 보고 통과시키지 말 것

모뎀이 자는 동안에도 **차키 명령이 제때 도착해야** 한다. AT 를 보내는 방향은
TinyGSM `sendAT` 훅이 자동으로 깨워 안전하지만, 반대 방향(모뎀이 URC 를 내며 스스로
기상)은 첫 바이트가 깨질 여지가 있고 그 경로가 하필 차키 명령(`+CMQTTRX*`)이다.

1. `msleep on` 상태에서 **1분 이상 유휴**를 두어 확실히 재운다(`msleep` 로 자는중 확인).
2. 서버에서 차키 명령을 보낸다. → 즉시 실행되는지, ack 가 올라가는지 확인.
3. 이걸 **최소 10회**, 매번 충분한 유휴 뒤에 반복한다. 1회 성공은 근거가 안 된다.
4. 유실이 관찰되면 RI 핀(GPIO33) 기상으로 넘어간다(`modempwr.h` 하단 참고).

같이 볼 것: 로그에 `[MQTT] 재접속됨` 이 잦아지지 않는지. 잦아지면 발행 ACK URC 가
새고 있다는 뜻이라 `MODEM_SLEEP_IDLE_MS` 를 키우거나 가드를 조여야 한다.

### 기록

| 조건 | 5V 평균 | 수면비율 | 차키 명령 10회 | 재접속 발생 |
|---|---|---|---|---|
| `msleep off` (기준선) | 120mA | 0% | | |
| `msleep on` | mA | % | | |

## 다음 작업 후보 (절감 기대치, 5V 기준)

| 작업 | 대상 | 기대 절감 | 위험 |
|---|---|---|---|
| ESP32 light sleep + CPU 80MHz | floor 63 → 15~25 | **−40~48mA** | 중(loop 주기·AT 응답 대기 재설계) |
| 모뎀 유휴 슬립 (`AT+CSCLK=1` + DTR 제어) | idle−floor 47 → 5~15 | **−32~42mA** | 중(URC 수신 타이밍 검증 필요) |
| 주차 중 GPS·OBD2 차단 | 정상−mqtt 30~80 → 0 | −30~80mA | 낮음(주행 판정 이미 있음) |
| 보드 정지전류(전원 LED 등) | floor 잔여 | −3~10mA | 낮음(HW 개조, 되돌리기 어려움) |

셋 다 적용 시 **25~35mA @5V** 가 현실적 목표다(mqtt 상태 120mA 대비 약 4배 개선).
차량 12V 쪽 최종 수치는 컨버터를 포함해 다시 재야 확정된다.

### 이미 확인된 사실 (계측 전 코드 조사)

- 절전 코드가 **하나도 없다**. `esp_sleep_*` / `setCpuFrequencyMhz` / `AT+CSCLK` / `AT+CPSMS` / `AT+CEDRXS` 전부 0건.
  ESP32 는 240MHz 로 한 번도 자지 않고 `loop()` 를 돈다.
- `modemPowerOn()` 이 DTR 을 LOW 로 고정해 **모뎀 슬립을 명시적으로 막고 있다**
  ([KeyplusDiagnostic.ino](../examples/KeyplusDiagnostic/KeyplusDiagnostic.ino) 의 `MODEM_DTR_PIN` 블록).
- 캐리어 NAT 가 유휴 TCP 를 60초에 끊는 게 실측으로 확인돼 있어
  ([config.h `MQTT_NAT_IDLE_TIMEOUT_MS`](../examples/KeyplusDiagnostic/config.h)),
  상시연결을 유지하는 한 60초마다 라디오를 깨워야 한다. **이게 "즉시 응답" 요구가 만드는 소비전류 하한이다.**
