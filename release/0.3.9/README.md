## 무슨 일이 있었나

260806 데일리 체크에서 `telemetry_fast` 건수가 이상했습니다. `fast_ms=1000`(1Hz)
설정인데:

| 구간 | 분당 샘플 | 실효 주기 |
|---|---|---|
| 주행 중 (12:52~13:01) | 28~38 (평균 33) | 약 1.8초 |
| 감속 중 (13:02~13:05) | 38 → 52 → 58 → 55 | 1.6 → 1.1초 |
| 시동 OFF 후 (13:06~13:34) | 57~58 | 1.03초 |

속도가 떨어질수록 촘촘해집니다. **필요한 순간에 가장 성기고 쓸모없는 정차 구간에서
가장 촘촘했습니다.**

그리고 이것이 이벤트 산출을 통째로 막고 있었습니다. 서버 `harsh_accel` 기본 룰은
`min_s=2` 로 **2초 지속**을 요구하는데, 1.8초 간격에서는 연속 2샘플이 1.8초에 그쳐
임계 지속을 영영 채울 수 없습니다. 임계값 문제가 아니라 입력이 어긋나 있었습니다.

같은 데이터에서 두 가지가 더 나왔습니다.

- **시속 48km 로 달리는 중에 `rpm` 이 0 인 행**이 있었습니다. ECU 미응답 PID 를
  0 으로 적고 있어 "엔진 정지"와 "값 못 읽음"이 DB 에서 구분되지 않았습니다.
- **13:06 시동 OFF 후 13:34 까지 28분간 수집이 계속**됐습니다. 그 시간대 1,942건 중
  1,678건(86%)이 정차분입니다 — 주행 16분을 담으려고 37분치를 저장한 셈이고,
  `telemetry_fast` 보관은 30일입니다.

## 왜 그랬나

구멍이 셋이고 원인이 각각 다릅니다.

### ① 페이싱 — 지터가 매 주기 더해졌다

다음 샘플 시각을 `now` 로 되잡고 있었습니다. 그러면 실효 주기가
`periodMs + 그 틱의 loop 지터`가 됩니다(`delay(50)` + `readFast` 약 60ms). 누적은
아니지만 매 주기 새로 더해지므로 1Hz 설정이 1.1Hz 주기가 됩니다.

### ② 슬롯 유실 — 이쪽이 주범이다

`s_lastSampleMs = now` 를 `readFast` **앞에서** 실행했기 때문에, 폴이 실패하거나
차속 PID 가 응답하지 않으면 그 슬롯을 쓰고도 샘플 없이 돌아갔습니다. 다음 기회는
꼬박 1초 뒤입니다. **정차 58 대 주행 33 의 격차는 대부분 이쪽**입니다 — 주행 중에는
ECU 가 전체 폴(11 PID)과 겹쳐 더 자주 빠집니다.

### ③ 게이트가 CAN 링크만 봤다

`obd.valid` 는 CAN 링크 생존이지 시동 상태가 아닙니다. 차량 CAN 은 시동을 꺼도
한동안 깨어 있어서, 그 구간이 `spd=0, rpm=0` 샘플로 계속 쌓였습니다.

`KeyplusDiagnostic.ino` 의 status 전이 판정은 이미 이 둘을 나눠 보고 있었습니다
(`power_mode` 는 링크로, `ignition_on` 은 rpm 으로). 고빈도 수집만 그 구분을 안
따르고 있었던 것입니다.

## 무엇을 고쳤나

- **고정 격자 페이싱** — 다음 시각을 `직전 격자 + periodMs` 로 전진시킵니다. 한 틱이
  늦게 와도 다음 격자가 앞당겨져 평균 주기가 유지됩니다. 한 주기 넘게 밀리면
  (`Gps::begin` 15초 블로킹 등) 격자를 재동기화해 몰아치기를 막습니다.
- **슬롯 회수(`retrySoon`)** — 폴 실패·차속 미응답 시 150ms 뒤 한 번 더 두드립니다.
  격자를 **당기기만** 하므로 실패해도 원래 주기로 복귀하고, `o` 오프셋(반올림 초)도
  흔들리지 않습니다.
- **결측 보존(`Sample.miss`)** — PID 미응답을 0 이 아니라 결측으로 들고 가서 발행 시
  그 자리에 JSON `null` 을 싣습니다. 집계·공회전 판정에서도 결측 초를 제외합니다.
  `miss` 바이트는 `rpm`(uint16_t) 정렬이 남긴 꼬리 패딩에 들어가 **구조체가 6바이트
  그대로**입니다(`static_assert` 로 고정, RAM 증가 0).
- **시동 OFF 게이트** — `rpm 확정 0 + 정지`가 5샘플 연속이면 수집을 중지하고 5초
  주기로 재시동만 확인합니다.

> ⚠️ **`rpm` 이 확정 0 일 때만** 시동 OFF 로 읽습니다. 결측을 0 으로 보면 링크가
> 불안정한 주행 구간이 시동 OFF 로 오판돼 수집이 멈춥니다 — 결측 보존이 이 게이트의
> 전제입니다. 신호대기 정차는 rpm 이 공회전(≈750)이라 걸리지 않습니다.

## 서버 선행 조건 (필수)

`keyplus-diagnostic-backend` 의 아래 커밋이 **선행 또는 동시 배포**되어야 합니다.

```
fix(gateway): 고빈도 결측을 0 으로 굳히던 numOrNull — 계약을 null 로 연다
```

`ingest.ts` 의 `numOrNull` 이 `Number(null) === 0` 을 그대로 통과시켜, 단말이 보낸
결측 `null` 을 서버가 도로 0 으로 굳히고 있었습니다. 이걸 안 고치면 **결측 보존이
통째로 무효**입니다.

펌웨어만 올려도 회귀는 없습니다 — 결측 항목만 0.3.8 과 같은 상태로 남습니다.
페이싱과 시동 OFF 종료는 서버와 무관하게 동작합니다.

## 배포 후 확인

`fast` 콘솔 한 번이면 세 항목을 같이 볼 수 있습니다.

```
fast
  샘플 주기      : 1000ms (1.0Hz)
  마지막 샘플    : off=12 spd=47 rpm=1820 thr=18  (- = 결측)
  PID 결측       : rpm 0 / thr 0
  폴 상태        : 정상            ← 시동 OFF 시 "중지(시동 OFF — rpm 회복 시 재개)"
```

DB 로는 다음 주행 뒤 이 둘을 봅니다.

1. **시간당 `telemetry_fast` 건수가 1,800 에 가까운가** (종전 주행 구간 약 2,000/시간
   이었으나 그 대부분이 정차분이었습니다 — 이제 주행 구간만 촘촘해야 합니다)
2. **`driving_events` 가 산출되는가**

2번이 여전히 0 이면 다음 의심 지점은 임계값(`harsh_accel` `a_ms2=3.0` / `min_s=2`)
입니다. **이 릴리스 전에는 샘플 간격 때문에 임계 판정 자체가 성립하지 않아 임계값을
검증할 수 없었습니다.**

## 알려진 미해결

- **실차 검증 전입니다.** 위 수치는 코드와 260806 실측에 근거한 예측입니다.
- `partner-api /vehicles` 응답은 `rpm`/`thr` 을 요청할 때 건수가 줄 수 있습니다.
  요청 필드 중 하나라도 `null` 이면 그 초를 통째로 빼는 기존 계약 때문입니다.
  가짜 0 이 사라지는 것이라 방향은 맞습니다. `spd` 만 요청하면 변화 없습니다.
- rpm PID 를 아예 주지 않는 차량에서는 시동 OFF 게이트가 서지 않아, 종전처럼 CAN 이
  깨어 있는 동안 수집이 이어집니다.
- 0.3.8 의 미해결(OTA HTTPS 다운로드 경로가 SSL ctx 0 를 MQTT 와 공유 — 실기 미검증)과
  0.3.7 의 미해결(KT/SKT APN 미검증)은 그대로 유효합니다.
