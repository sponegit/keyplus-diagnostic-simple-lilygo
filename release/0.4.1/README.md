### 원인 확정 — `err=-13` (ACCQ)

3회 모두 동일했습니다. 후보 둘 중 CA 업로드(`-10`)가 아니라 **ACCQ** 였습니다.

```
[10:41:42] [BUF] 백필 ts=1786071855 FAILED (155 B)
[10:41:42] [MQTT] 연결 끊김 — 백오프 재접속 시작
[10:41:46] [MQTT] 접속 실패 err=-13 (ACCQ(서비스 미시작 추정)) — 연속 1회
[10:41:46] [MQTT] ACCQ 실패 — 모뎀에 CMQTT 서비스 없음, 재시작
[10:41:54] [MQTT] 접속됨 (TLS, 서버 CA 검증)
```

세션이 끊긴 뒤 **모뎀이 CMQTT 클라이언트 0 을 놓지 않습니다.** `CMQTTREL` 이 안 먹고
`CMQTTACCQ` 가 "이미 점유"로 거부합니다. 0.3.9 가 재부팅 전까지 영영 못 붙은 이유가
이걸로 완전히 설명됩니다 — `s_serviceStarted` 가 참이라 `mqtt_begin`(CMQTTSTART)을
건너뛰었고, 그 상태를 푸는 유일한 방법이 CMQTTSTOP→START 였는데 그 경로가 없었습니다.

승격 2단계(데이터패스 검증)·3단계(모뎀 리셋)는 **0회** — ACCQ 지름길에서 전부
끝났습니다. 설계 의도대로입니다.

> 0.4.0 릴리스 노트에 미해결로 남겼던 **`[MQTT] 연결 끊김` 부재**도 해소됐습니다.
> 이번엔 정상 출력되고 바로 앞에 `[BUF] 백필 ... FAILED` 가 찍혔습니다 —
> 캡처 유실이 맞았고, 세션 사망 경로에 구멍은 없습니다.

## 0.4.1 이 고치는 것

[`backfillGateOpen`](../../examples/KeyplusDiagnostic/KeyplusDiagnostic.ino) 의 주석은
이렇게 적혀 있습니다.

> 모뎀은 publish 를 1건씩만 처리하고 겹치면 세션이 깨진다 — 가드가 이 펌웨어의 생명줄이다.

그런데 정작 가드는 **1초 벽시계 타이머**뿐이었습니다. 직전 QoS1 의 PUBACK 이 실제로
도착했는지는 보지 않습니다. PUBACK 이 1초를 넘으면 다음 백필이 그 위로 겹쳐 나갑니다.

추측할 이유가 없습니다 — 0.3.8 의 P3 가 결과 URC(`+CMQTTPUB`)를 이미 파싱해 두고
있고(`mqttPubAckPending`), **구독 경로는 그 신호를 씁니다.** 백필만 안 썼습니다.

```c
if (Mqtt::pubAckPending(modem)) return false;   // 직전 발행이 아직 안 끝났다
```

- **백필에만 겁니다** — 초당 1건이 몇 분씩 이어지는 경로는 이것뿐입니다.
  telemetry(30초)·fast·status 는 간격이 넓어 겹칠 여지가 사실상 없습니다.
- **굶지 않습니다** — URC 가 끝내 안 오면 8초(`MQTT_PUB_ACK_TIMEOUT_MS`)에
  `pubAckOverdue` 가 세션을 사망 처리하므로 대기가 그 안에서 끝납니다.
- **순서** — 게이트 호출 지점이 `Mqtt::handle()` 뒤라 URC 가 펌핑된 뒤 평가됩니다.

## ⚠️ 이 변경이 발병을 고친다는 근거는 없습니다

0.4.0 실측에서 3회 발병이 **모두 백필 발행에서** 터졌습니다. 그러나 전체 발행 847건 중
백필이 751건(89%)이라 **우연과 구분되지 않습니다.**

| | |
|---|---|
| 발행 실패율 | 3 / 847 = **0.35%** |
| 발병 시 신호 | rssi **31** (최상). 전 구간 26~31 |
| 부하 의존성 | 마지막 발병 뒤 **백필을 계속 돌리며 11분간 무사** |

즉 원인 규명이 아니라, **코드가 스스로 정한 규칙을 지키지 않던 자리를 메우는 변경**입니다.

## 배포 후 확인

**판정 기준이 명확하지 않다는 점을 먼저 아셔야 합니다.** 발병이 25분에 3회로
산발적이라, 개선 여부를 보려면 비슷한 주행 조건에서 **여러 세션의 발병 빈도**를
비교해야 합니다. 한 번 타보고 안 터졌다고 고쳐진 것이 아닙니다.

기록해 둘 값 셋:

```
grep -c "연결 끊김"        # 세션당 발병 횟수
grep -c "err=-13"          # 전부 -13 인가 (다른 값이면 새 경로)
grep -c "백필.*published"  # 발행량 — 발병률의 분모
```

회귀만 빠르게 볼 항목:

- 백로그 소진 속도가 눈에 띄게 느려졌는가 (`[STAT]` 의 `buf=` 감소율).
  PUBACK 지연 구간에서 그만큼 느려지는 건 의도된 트레이드오프이나, 체감될 만큼
  느려지면 `BACKFILL_MIN_GAP_MS` 재검토가 필요합니다.

## 알려진 미해결

- **세션이 왜 끊기는지는 여전히 미규명입니다.** 단말 로그로는 "모뎀이 CMQTT 클라이언트를
  놓지 않는다"까지가 한계입니다. 다음 후보는 **서버(EMQX) 로그** — 260810 의
  10:41:42 / 10:47:49 / 10:49:24 세 시각에 브로커가 이 `client_id` 를 어떤 이유로
  끊었는지가 남아 있을 것입니다.
- **더 싼 수정이 남아 있을 수 있습니다.** ACCQ 가 "이미 점유"로 실패하는 것이라면,
  `mqtt_connect` 가 `CMQTTREL` 앞에 `CMQTTDISC` 를 한 번 보내는 것만으로 실패 자체가
  없어지고 복구가 12초에서 더 줄 수 있습니다(현재는 CMQTTSTOP→START 사이클을 돕니다).
  미검증이라 이번에는 넣지 않았습니다.
- `Mqtt::stopService()` 는 CMQTTDISC/REL/STOP 3연속 AT 라 최악 십수 초 블로킹입니다.
  승격당 1회뿐이라 감수합니다.
- 모뎀 하드 리셋까지 갔는데도 안 붙는 경우는 다루지 않습니다.
- `lib/TinyGSM` 포크에 0.4.0 의 변경이 있습니다. 포크를 갱신하면 덮입니다.
- 0.3.9(고빈도 수집 실차 미검증), 0.3.8(OTA HTTPS 경로 SSL ctx 공유 미검증),
  0.3.7(KT/SKT APN 미검증)의 미해결은 그대로 유효합니다.
