## 무엇을 고쳤나

차량에 설치하면 하루를 못 버티던 문제입니다. 실측 150~200mA 였습니다.

**펌웨어만으로 −81mA를 확보했습니다.** 주차 상태 기준 150~200mA → 85~105mA.

| 항목 | 절감 | 근거 |
|---|---|---|
| CPU 240 → 80MHz | **−36mA** | floor 63 → 27mA |
| 주차 중 GNSS 전원 차단 | **−45mA** | 150 → 105mA, **같은 실행 안 측정** |

### ① CPU 클럭 240 → 80MHz

ESP32 가 240MHz 로 한 번도 쉬지 않고 돌고 있었습니다. 클럭에 거의 비례해 먹으므로 그대로 절감됩니다.

⚠️ **80MHz 가 안전한 바닥입니다.** 그 아래로 내리면 APB 가 CPU 를 따라 내려가 **UART 보레이트가 전부 어긋나** 모뎀 통신과 콘솔이 통째로 깨집니다. `config.h` 에서 `#error` 로 컴파일 단계에 차단해 뒀습니다.

주변장치(TWAI 500kbps · UART · 타이머)는 APB 80MHz 고정이라 영향이 없습니다. CPU 바운드 작업(JSON 조립, 로그 출력)만 3배 느려집니다.

부팅 배너에 `cpu : 80MHz` 가 찍힙니다.

### ② 주차 중 GNSS duty cycle

종전에는 **GNSS 엔진이 부팅 때 켜진 뒤 한 번도 꺼지지 않았습니다.** `Gps::end()` 는 구현만 있고 호출되지 않았습니다. 그래서 폴링 주기를 10초→60초로 늘려도 수신기는 계속 돌며 45mA 를 먹었습니다 — **주기는 전력 레버가 아닙니다.**

주차 판정(`vehicleMoving` 재사용) 시 `AT+CGNSSPWR=0` 으로 엔진을 끄고, 5분마다 켜서 최대 90초 측위 후 다시 끕니다. 주행 재개 시 즉시 상시 ON 으로 복귀합니다.

설계에서 특히 조심한 세 가지:

- **비블로킹** — `Gps::powerOn()` 을 신설했습니다. 기존 `Gps::begin()` 은 실패 시 최대 15초를 잡는데, 5분마다 그러면 **차키 명령이 밀립니다.** 즉시 응답이 이 제품의 제1 요구라 절전이 그걸 깨면 본말전도입니다.
- **"GNSS 꺼짐 = 모뎀 리부팅" 오판 차단** — 기존 코드에 그 판정이 있어, 우리가 끈 걸 사망 신호로 읽으면 **멀쩡한 MQTT 세션을 스스로 끊습니다**(과거 같은 함정으로 107초를 날린 기록이 코드 주석에 있습니다). `g_dutyOff` 로 의도적 OFF 를 구분합니다.
- **끄기 실패를 삼키지 않음** — `Gps::end()` 가 반환값을 내도록 바꿨습니다. 실패했는데 껐다고 믿으면 조회만 건너뛴 채 GNSS 가 계속 돌아 45mA 를 태우는데, **로그는 OFF 라 눈으로는 절대 못 찾습니다.**

측위 실패가 이어지면 주기를 지수 백오프(5→10→20→30분)합니다. 지하주차장처럼 영영 측위가 안 되는 곳에서 5분마다 90초씩 켜면 duty 30% → 약 13mA 를 소득 없이 태우는데, 30분 주기면 2mA 로 접힙니다. 한 번이라도 측위되면 즉시 5분으로 복귀합니다.

로그로 TTFF 를 남깁니다:

```
[GPS] duty: 측위 18s 만에 완료 → GNSS OFF (평균 TTFF 21s, 3회, 다음 5분)
[GPS] duty: 90s 안에 측위 실패 → GNSS OFF (다음 시도 10분 뒤)
```

## 시도했으나 채택하지 않은 것

기록으로 남깁니다. 같은 길을 다시 파지 않기 위해서입니다.

| 시도 | 결과 | 이유 |
|---|---|---|
| 모뎀 유휴 슬립 `AT+CSCLK` | **효과 0** | AT 매뉴얼이 이 명령을 "Control **UART** Sleep"으로 규정한 그대로다. UART 를 재워도 모듈 baseline 은 안 줄어든다 |
| ESP32 light sleep | **불가** | 자는 동안 APB 가 꺼져 UART 바이트가 유실된다. 차키 명령이 그 경로다 |
| CAN 핀 열성 주차 | 효과 0 | 상태 위생 목적으로만 유지 |

### 모뎀 슬립이 안 되는 이유 — 배선

`AT+CSCLK=1`(DTR 슬립)은 **이 보드에서 걸리지 않습니다.** `msleep probe` 가 "재운 뒤에도 AT 응답"을 냈는데, A7670 HW 매뉴얼 3.3.2 는 "CSCLK=1 에서 DTR 을 올리면 串口功能不能正常通讯"(UART 통신 불가)라고 명시합니다 → **GPIO25 가 모듈 DTR 핀에 닿아 있지 않습니다.**

`AT+CSCLK=2`(RX 슬립, 핀 불필요)로 우회해도 전류 변화가 없었고(같은 실행 A/B: on 60mA / off 58mA, 기상 지연 4ms / 4ms), **오히려 `msleep on` 1분 뒤 세션이 끊긴 정황**이 있습니다. 이득 0 에 위험만 있어 `FEATURE_MODEM_SLEEP=0` 으로 껐습니다(코드는 계측 도구로 남겨 뒀습니다).

### light sleep 이 안 되는 이유 — 역시 배선

RI(GPIO33)도 **670초 동안 엣지 0회**였습니다(그 사이 URC 20회 이상). 미배선입니다.

RI 가 유일한 답이었던 이유는 모뎀이 URC 본문보다 **60ms 앞서** 통지를 주기 때문입니다. 그게 없으면 어떤 기상 소스를 써도 복귀 지연(약 1ms = 115200bps 에서 11바이트) 동안 `+CMQTTRX` 헤더가 잘리고, 모뎀은 재전송하지 않으므로 **차키 명령이 영구히 사라집니다.**

> **이 보드에서 `utilities.h` 의 핀 정의는 실제 배선을 보장하지 않습니다.**
> DTR(GPIO25)·RI(GPIO33) 둘 다 미배선이었습니다. TXD/RXD/PWRKEY/RESET/POWERON 만
> 실제로 물려 있다고 보는 편이 안전합니다. 다음에 핀에 의존하는 설계를 하기 전에
> **반드시 실측으로 확인하십시오.**

## 계측 도구 (`PWR_BENCH`)

`config.h` 의 `PWR_BENCH` 한 줄로 기능 조합을 바꿔 소비전류를 분해합니다. **출고 기본은 0** 입니다.

| 값 | 구성 | 용도 |
|---|---|---|
| 0 | 정상 (전체 기능) | 출고 |
| 1 | 모뎀 유휴, LTE off | 모뎀 몫 |
| 2 | LTE+MQTT 만 | 기준선 |
| 3 | 모뎀 OFF, ESP32+보드만 | **바닥 / 계측기 교정** |
| 4 | 2 + GNSS 만 | GNSS 몫 |
| 5 | 2 + OBD2/CAN 만 | CAN 몫 |

빌드·플래시는 `bench/flash.sh <모드>`, 절차와 기록은 `bench/README.md` 를 보십시오.

### 계측 규칙 — 이걸 어겨서 세 번 잘못된 결론에 이르렀습니다

1. **매 세션을 모드 3(floor)으로 시작해 27mA 근처인지 확인합니다.** 모뎀이 꺼져 있어 전파 상태에 영향받지 않는 유일한 재현 가능 기준점입니다. 안 맞으면 그 세션 값은 쓰지 않습니다.
2. **같은 실행 안의 토글 결과만 근거로 삼습니다.** 실행 간 비교는 못 씁니다 — **RSSI(하향 수신세기)는 상향 송신 전력을 예측하지 못합니다.** 같은 rssi=29 에서도 세션에 따라 PA 전류가 크게 달라, 동일 펌웨어·동일 설정에서 mode 2 가 60mA 와 150mA 로 갈린 사례가 있습니다.
3. **배터리 수명 판단에는 수 시간 평균이 필요합니다.** 5분 스냅샷은 모뎀 변동 구간을 우연히 잡습니다.

## 남은 과제

**차량 12V 하네스 실측이 아직 없습니다.** 지금까지 전부 Nordic PPK2 가 **5V 를 직접 공급**한 값이라, 차량용 12V→5V 컨버터가 통째로 빠져 있습니다. 경부하 효율이 30~50% 인 벅 컨버터라면 5V 부하를 줄인 이득이 크게 깎입니다.

**"하루 이상 버티는가"는 그 조건에서 수 시간 이상 재야 답이 나옵니다.**

더 내리려면 남은 것은 모뎀 유휴(약 47mA)와 ESP32 활성(27mA)인데, 둘 다 **펌웨어 수단이 없습니다.** 선택지는 RTS/CTS 또는 RI 배선(하드웨어 개조), 컨버터 교체, 발행 주기 완화(NAT 60초 한계 안에서 30→45초)입니다.
