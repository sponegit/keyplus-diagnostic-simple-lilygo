## OBD2 — 응답 ECU를 고정하지 않아 데이터가 섞이던 문제 (0.2.10)

기능 요청(`0x7DF`)에는 **여러 모듈이 각자 답합니다.** 기존 코드는 `0x7E8~0x7EF` 중
**먼저 도착한 프레임**을 채택해서, 실차에서 세 가지 증상이 한꺼번에 나왔습니다.

| 증상 | 원인 |
|---|---|
| 지원 PID 마스크가 부팅마다 다름 (`0x80100001` / `0x983BA013` / `0x98188003`) | 마스크를 준 모듈이 매번 달랐다. `0x80100001` 은 PID `0x01/0x0C/0x20` 만 지원하는 보조 모듈의 마스크 |
| `rpm=16384` 가 70초간 발행 | 엔진 아닌 모듈이 `0x0C` 에 `FF FF`(데이터 없음)로 답했고 그대로 `0xFFFF/4` 로 디코드 |
| VIN 조회 실패 `FF=0 got=0/0` | 멀티프레임도 같은 문제 — 엉뚱한 모듈 프레임을 보고 Flow Control 을 잘못된 주소로 보내 재조립이 깨졌다 |
| `0xA6`(오도미터) 미지원 오래치 | 시동 직후 폭주 구간의 무응답으로 지원 PID 를 영구 포기 |

### 수정

- **응답 ECU 고정.** 링크 확립 시 `0x00` 조회 창을 끝까지 열어 응답을 모으고 **엔진
  (`0x7E8`) 우선 채택**, 그 ID 를 이후 폴링·VIN 에 고정합니다. 엔진이 답하지 않으면
  경고를 남깁니다.
- **FF 채움 필터.** 응답이 전부 `0xFF` 면 "데이터 없음"으로 버립니다. 단 1바이트
  백분율 PID(`0x04` 부하 / `0x11` 스로틀 / `0x2F` 연료)는 **예외** — `0xFF`=100% 가
  실제로 가능한 값(전개 가속·만탱크)이라 버리면 정상 샘플을 잃습니다.
- **미지원 래치 조건 강화.** 확장 PID 무응답을 "같은 폴에서 고정 ECU 가 다른 PID 엔
  답하고 있을 때"만 카운트하고, 임계를 3→5 로 올렸습니다.
- **VIN 재시도 페이싱.** 매 폴 재시도라 상한 5회가 25초에 소진돼 세션 내내 VIN 을
  못 얻었습니다 → 5폴에 1회, 상한 8회(약 4분에 걸쳐 시도).
- `status obd` 에 **응답 ECU**와 VIN 재시도 진행 표시. VIN DEBUG 로그는 값이 바뀔
  때만 출력(5초마다 한 줄씩 찍혀 로그가 두 배였습니다).

### 실차 검증 (현대 팰리세이드 LX2 2023)

```
[OBD2] 링크 확립 @500kbps ECU=7E8 지원PID(01-20)=0x983BA013
[OBD2] VIN=KMHR281ABRU663944
[OBD2] rpm=800 spd=0 cool=67C load=16% thr=18% intake=39C maf=6.4g/s
       batt=13.86V run=685s odo=33100.1km
```

| 항목 | 0.2.8 | 0.2.10 |
|---|---|---|
| 응답 ECU | 매번 다름 | **7E8 고정** |
| 지원 마스크 | 부팅마다 3종 | **0x983BA013 고정** |
| rpm | 16384 (70초간) | **796~804** 처음부터 |
| VIN | 5회 실패 후 미확보 | **링크 확립 즉시** |
| 오도미터 | 미지원 오래치 | **33100.1km** |

> `PID 0x2F 미지원 확정` 은 이 차량이 실제로 연료잔량 표준 PID 를 노출하지 않는 결과이며,
> 래치가 **의도대로 동작한 것**입니다. 연료잔량이 필요하면 오도미터의 `22 B002` 처럼
> 제조사 UDS 경로를 따로 뚫어야 합니다.

## GPS — 첫 fix 15분 → 27초 (0.2.9)

- **위성군 지정 누락**이 주원인이었습니다. `Gps::begin()` 이 `AT+CGNSSPWR=1` 만 보내고
  `AT+CGNSSMODE` 를 안 보내 모뎀 기본값에 맡겼습니다. LilyGO 의 A7670 GNSS 예제들은
  전부 `GNSS_MODE_GPS_BDS_GALILEO_SBAS_QZSS`(=4)를 명시하는데, 우리가 참고한
  `GPS_BuiltIn` 예제에만 그 호출이 없어 빠졌습니다.
- **AGPS(`AT+CAGPS`)** 를 PDP up 직후 1회 시도합니다(`GPS_USE_AGPS` 토글, best-effort).
- **모뎀 리셋 후 GNSS 유실 수정.** 모뎀이 리셋되면 `AT+CGNSSPWR` 이 0 으로 돌아가는데
  `Gps::begin()` 은 setup 에서 한 번뿐이라 그 뒤로 **영구 미측위**였습니다(9시간 무측위
  사례). 리셋 직후 재활성화 + 연속 미측위 3회마다 `AT+CGNSSPWR?` 확인(백스톱).
- **미측위 진행 리포트(60초 주기 INFO)** — 미측위는 로그가 완전히 침묵해서 폴이 도는지도
  알 수 없었습니다. 경과 시간 + 원시 `+CGNSSINFO` 를 남깁니다:
  ```
  [GPS] 미측위 275s 경과 — raw: ,,,,,,,,        ← 필드 전부 공백 = 포착 위성 0 (RF/배치 문제)
  [GPS] 미측위 35s 경과 — raw: 2,05,03,,,...    ← 위성 잡히는 중 (기다리면 fix)
  [GPS] 미측위 60s 경과 — raw: (응답 없음 ...)   ← GNSS 엔진 문제
  ```
- 좌표가 NMEA `ddmm.mmmmmm` 로 오는 펌웨어 대비 방어 변환을 넣었습니다. 위도 90 / 경도
  180 초과일 때만 변환하므로 **이 모뎀(10진수 반환)에서는 no-op** 입니다(실측 확인).
- `status gps` 에 GNSS 엔진 on/OFF, 위성군, 원시 `+CGNSSINFO` 추가.
- **콘솔 `at <명령>` 패스스루 추가** — 현장에서 재플래싱 없이 모뎀에 직접 질의합니다.
  `at+cgnssinfo`, `at+cgnsspwr?`, `at+cgnssmode?` 등. 붙여쓰기/띄어쓰기 모두 받고,
  URC 를 먼저 비워 응답 오독을 막습니다.

실측: GNSS 활성화 후 **27초에 fix=3 / 16위성 / PDOP 1.2~1.6**, 좌표 `36.322273,127.375267`.

## 파일 구성

```
keyplus-diagnostic-0.2.10.bin       OTA로 내려보낼 이미지 (app 파티션 전용)
keyplus-diagnostic-0.2.10.bin.md5   MD5 한 줄 (배포 서버 검증용)
ota-manifest.json                   배포 메타 (버전/크기/해시/변경점) — url 채워서 사용
ota_start.json                      MQTT 명령 템플릿 — url/command_id 채워서 발행
```

> ⚠️ 이 `.bin`은 **app 이미지**입니다. USB로 처음 굽는 `0x0` 통합 이미지가 아닙니다.
> 시리얼 최초 플래싱은 `pio run -t upload`을 쓰세요.

## 배포 절차

1. `keyplus-diagnostic-0.2.10.bin`을 HTTP(S)로 접근 가능한 곳에 올린다.
2. `ota-manifest.json`의 `url`을 실제 주소로 채워 배포 기록으로 남긴다.
3. `ota_start.json`의 `command_id`(UUID)와 `url`을 채운다.
4. 대상 단말의 **`v1/{device_id}/cmd`** 토픽으로 발행한다 (QoS 1).
   예: `v1/vt-2607-0003-kfo/cmd`
5. 단말이 다운로드 → 플래시 → 재부팅한다.
6. 재부팅 후 MQTT 재접속되면 **`v1/{device_id}/cmd/ack`** 로 결과가 올라온다.

## ⚠️ 반드시 지킬 제약

### 1. 명령 JSON은 **약 1,000 바이트 미만**이어야 한다

래퍼(`TinyGsmMqttA76xx`)가 토픽과 페이로드를 **하나의 버퍼에** 나눠 담기 때문에,
토픽 길이만큼 페이로드 여유가 줄어듭니다(1024B − 토픽 24B ≈ 1,000B). 넘치면
**경고 없이 잘리고**, 잘린 JSON은 `url`이 빈 값이 되어 `[OTA] 잘못된 URL`로 실패합니다.

발행 전 확인:
```bash
python3 -c "import json;print(len(json.dumps(json.load(open('ota_start.json')),separators=(',',':'))),'bytes')"
```

### 2. `version`은 `0.2.10`과 **정확히** 일치해야 한다

재부팅 후 실행 이미지의 `FW_VERSION`과 대조해 ack를 결정합니다(`ota.cpp`).
불일치하면 실제로는 성공했어도 **`failed`로 ack**가 나갑니다.
**서빙하는 bin과 `version` 필드가 같은 릴리스인지 확인하세요** — 0.2.6 bin을
`version: 0.2.7`로 내려 ack가 failed로 나간 사례가 있습니다.

### 3. URL은 `http`로 시작해야 한다

`ota.cpp`가 `url.startsWith("http")`로 1차 검증합니다. HTTPS 권장.

### 4. 다운로드 중에는 MQTT가 끊긴다

모뎀의 SSL 컨텍스트를 HTTP(S)에 양보하려고 `Mqtt::stopService()`를 먼저 호출합니다.
그래서 ack는 즉시 나가지 않고 **재부팅 후 재접속 시점에 발행**됩니다(NVS pending).

### 5. 재부팅 후 10분 안에 MQTT에 붙어야 확정된다

새 이미지는 `PENDING_VERIFY` 상태로 부팅하고, MQTT 접속에 성공해야
`Ota::onHealthy()`가 확정(`mark_valid`)합니다.
`OTA_CONFIRM_DEADLINE_MS`(10분) 안에 못 붙으면 **자동 롤백 재부팅**됩니다.

→ 전파가 약한 곳이나 **전원이 불안정한 차량에서는 OTA를 피하세요.**

> 0.2.7~0.2.10의 부팅 견고화·복구 단축은 **OTA 확정 조건과 무관**합니다.
> 확정 조건은 여전히 "10분 내 MQTT 접속"입니다.

## 발행 예시

```bash
mosquitto_pub -h mqtt-dev.keyplus.sponeinfra.com -p 40102 \
  --cafile ca.pem \
  -u vt-2607-0003-kfo -P '<mqtt_pw>' \
  -t 'v1/vt-2607-0003-kfo/cmd' -q 1 \
  -f ota_start.json
```

## 배포 전 체크리스트

- [ ] 업로드한 파일의 MD5가 위 값과 일치 (`md5 -q <file>`)
- [ ] 서빙하는 bin이 **0.2.10 릴리스의 것**인지
- [ ] URL이 단말에서 접근 가능 (사설망/방화벽 확인)
- [ ] `ota_start.json` 직렬화 길이 **< 1,000 bytes**
- [ ] `version` 필드가 `0.2.10`
- [ ] 대상 단말이 **`cmd` 구독 성공** 상태 — `status server`에서 `[ok]` 확인
- [ ] 단말 전원 안정 (브라운아웃 이력 없음 — `info`의 `reset` 확인)
- [ ] 1대 선행 배포 후 확대

> **0.2.6 / 0.2.1 은 사용하지 마세요.** 0.2.6은 `FW_VERSION` 누락으로 ack가 항상
> `failed`, 0.2.1은 모뎀 리셋 후 MQTT 영구 접속불가 결함이 있습니다.
