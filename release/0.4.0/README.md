## 무슨 일이 있었나

260810 로그 2건에 같은 단말의 발병이 두 번 담겨 있습니다.

| | 구간 | 결과 |
|---|---|---|
| 1차 | 09:12 무렵 ~ 09:38 | 25분+ `mqtt=OFF`, 미전송 백로그 1,507건. 사용자가 재부팅 |

15초 간격으로 같은 한 줄만 반복됩니다.

재부팅하면 **같은 CA·같은 비번·같은 APN 으로 5초 만에** 붙습니다. 크리덴셜 문제가
아니라 모뎀 쪽 상태 문제라는 뜻입니다.

로그로 배제되는 것들:

- **망 아님** — rssi 24~29 유지, `[LTE] 링크 다운`·`재브링업` 0회
- **모뎀 사망 아님** — 미접속 구간에도 `[STAT]` 이 rssi 를, `[PWR]` 이 온도를 AT 로
  읽습니다. 모뎀은 멀쩡히 응답 중이었습니다
- **전원·발열 아님** — vbat 4,274~4,286 mV 안정, 34~37 °C

## 왜 스스로 못 빠져나왔나

승격 트리거가 둘 있었는데 **이 상태에는 둘 다 걸리지 않습니다.**

| 트리거 | 왜 안 걸리나 |
|---|---|
| LTE 재브링업 → 모뎀 리셋 | `Lte::isUp()`(등록+PDP)이 계속 참이라 진입조차 안 함 |
| CMQTTSTART 실패 → 모뎀 리셋 | `s_serviceStarted` 가 참이라 `mqtt_begin` 을 건너뜀 → `serviceStartFails` 는 영원히 0 |

**세션 접속(`CMQTTCONNECT`) 실패를 세는 카운터가 아예 없었습니다.** 백오프만 15초에서
포화되고 그 자리를 계속 돕니다.

## 무엇을 고쳤나

### ① 자력 복구 — 단계 승격

싼 것부터, 각 단계가 서로 다른 원인을 겨눕니다.

| 시점 | 동작 |
|---|---|
| ACCQ 실패 즉시 | CMQTT 서비스 재시작 (모뎀에 서비스가 없다는 뜻이라 원인 확정) |
| 4회 연속 (약 1분) | **데이터패스 실검증(HTTP GET)** → 죽었으면 PDP 재브링업, 살았으면 서비스 재시작 |
| 그 뒤 4회 더 (약 2분) | 모뎀 하드 리셋 = 사용자가 하던 재부팅의 자동화판 |

데이터패스 실검증이 필요한 이유: `Lte::isUp()` 은 등록·PDP 만 봅니다. 캐리어가 세션을
반쯤 놓은 **좀비 PDP**(등록은 살아있고 실제 패킷은 안 나감)는 그 둘을 통과합니다.
부팅 때만 하던 HTTP GET 을 여기서 한 번 태워 "망이 죽었나 / 브로커만 안 붙나"를
실제로 가릅니다.

> 2차 발병 타임라인에 대입하면 첫 실패로부터 **약 95초 만에** 자력 복구 시도가 끝납니다.
> 실제 로그는 그 시점에도 여전히 죽어 있었습니다.

### ② 원인을 남긴다

`mqtt_connect()` 는 실패 경로가 여덟 군데인데 전부 그냥 `false` 를 냈습니다. 지점
식별자를 붙였습니다.

```
[MQTT] 접속 실패 err=-13 (ACCQ(서비스 미시작 추정)) — 연속 3회
```

| err | 뜻 |
|---|---|
| `-10` | CA PEM 업로드 실패 |
| `-13` | CMQTTACCQ 실패 (서비스 미시작 / 클라이언트 점유) |
| `-14` | LWT 등록 실패 |
| `-15` | CMQTTCONNECT 명령 거부 |
| `-16` | CONNECT 결과 URC 미도착 |
| 양수 | 모뎀이 준 err — 브로커/TLS 거절 |

같이 고친 버그: `+CMQTTCONNECT` 의 err 을 `stream.read()` **한 바이트**로 읽고
있었습니다. err 이 두 자리(19, 21 등)면 뒷자리가 스트림에 남아 다음 `waitResponse` 를
오염시킵니다.

### ③ 실패가 loop 를 멈추던 시간

로그에서 직접 잽니다 — OBD 5초 폴·GPS 10초 폴이 사라진 구간이 그대로 정지 구간입니다.

| 시점 | 정지 |
|---|---|
| 09:46:10 (1회차) | 11초 |
| 09:49:14 직전 | **44초** (OBD 8회·GPS 4회·`[STAT]` 1회가 통째로 빠짐) |

오프라인 버퍼의 존재 이유가 "못 보내는 동안에도 계속 모은다"인데, 정작 그 구간에서
수집이 45초씩 멈췄습니다. 차키 응답도 같이 밀립니다.

대기를 **무엇을 기다리는가**로 갈라 값을 줬습니다.

| 대상 | 종전 | 변경 |
|---|---|---|
| 모뎀 로컬 `>` 프롬프트 5곳 (CCERTDOWN ×3, WILLTOPIC, WILLMSG) | 10초 | **3초** |
| 로컬 설정 OK 2곳 (`CMQTTCFG`, `CMQTTCONNECT` 접수) | 30초 | **5초** |
| `+CMQTTCONNECT` 결과 URC | 30초 | **30초 유지** |

> ⚠️ 마지막 줄은 TLS 핸드셰이크 + CONNACK 왕복입니다. LTE 에서 5~10초가 정상이라
> 줄이면 **멀쩡한 접속이 실패합니다.** 이제 이 자리가 30초짜리 유일한 대기입니다.

실패 지점별 상한: CA 업로드 4초 / ACCQ 3.5초 / CMQTTCFG 5초 / LWT 4초 / CONNECT 접수 5초.

### ④ CA 재기록

접속 실패마다 인증서 캐시를 비워 15초마다 1.9 KB PEM 을 모뎀 플래시에 다시 썼습니다.
1차 발병의 25분이면 약 100회입니다. 그 교착은 결국 재부팅으로만 풀렸으니 재업로드는
회복에 기여하지 못했고 플래시 수명만 깎았습니다 → 최소 60초 간격을 뒀습니다.

## 배포 후 확인

**1. 정상 접속 회귀가 최우선입니다.**

```
[LTE] 데이터패스 검증 성공 (HTTP 200)
[MQTT] begin: TLS+sni, broker ...
[MQTT] 접속됨 (TLS, 서버 CA 검증)      ← 여기까지 5초 안팎
```

여기가 늘거나 실패하면 유지하기로 한 TLS 핸드셰이크 대기(30초)를 잘못 건드린 것입니다.
즉시 0.3.9 로 되돌리세요.

**2. 교착이 재현되면 볼 것 셋.**

- `접속 실패` 줄 **사이에 OBD 5초 폴이 끊기지 않고** 찍히는가 → ③의 판정 기준
- `err=` 값이 `-10`(CA 업로드)인지 `-13`(ACCQ)인지 → 원인 확정
- 첫 실패로부터 약 60초 안에 승격 줄이 나오는가

```
[MQTT] 접속 4회 연속 실패(데이터패스는 정상) — CMQTT 서비스 재시작
[MQTT] 서비스 재시작 후에도 접속 4회 실패 — 모뎀 리셋
```

**3. 콘솔로도 같은 값을 봅니다.**

```
status server
  연속 접속실패  : 2회 (4회에 데이터패스 검증+서비스 재시작)
  마지막 실패    : -13
```

## 알려진 미해결

- **실차 검증 전입니다.** 위 회복 시간은 코드와 260810 실측 타임라인에 근거한 예측입니다.
- **260810 교착의 정확한 실패 지점은 아직 미확정입니다.** 재부팅으로 회복됐다는 사실이
  "모뎀 쪽 상태"까지만 말해주고, 그 로그에는 에러코드가 없어 `-10` 과 `-13` 중 하나로만
  좁혔습니다. 이 릴리스가 그 근거를 남기므로 재현되면 특정됩니다.
- **260810 로그2 에 `[MQTT] 연결 끊김` 이 0회입니다.** `s_connected` 를 내리는 모든 경로가
  한 줄씩 남기는데(`FAILED` 0, `무응답` 0, `리셋 정황` 0) 끊긴 흔적이 없습니다 — 코드상
  성립할 수 없는 조합이라 캡처 유실로 보고 있으나 확정하지 못했습니다. 다음 캡처에서 이
  줄이 정상적으로 찍히는지 확인이 필요합니다. 안 찍힌다면 세션 사망 경로에 아직 모르는
  구멍이 있다는 뜻입니다.
- `Mqtt::stopService()` 는 CMQTTDISC/REL/STOP 3연속 AT 라 최악 십수 초 블로킹입니다.
  승격당 1회(약 1분에 한 번)뿐이라 이번에는 감수했습니다.
- 모뎀 하드 리셋까지 갔는데도 안 붙는 경우는 다루지 않습니다. 그 뒤로는 종전처럼 15초
  백오프 재시도만 돕니다.
- `lib/TinyGSM` 포크에 변경이 있습니다. 포크를 갱신하면 이 변경이 덮입니다.
- 0.3.9(고빈도 수집 실차 미검증), 0.3.8(OTA HTTPS 경로 SSL ctx 공유 미검증),
  0.3.7(KT/SKT APN 미검증)의 미해결은 그대로 유효합니다.
