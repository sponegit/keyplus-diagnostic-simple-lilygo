## 🔴 배포 순서를 지키세요 — UART 앱이 **먼저**입니다

이 펌웨어는 `[STAT]` 한 줄에 `buf=` / `fast=` 토큰을 추가합니다.

```
[STAT] up=142s mqtt=on rssi=19 gps=fix/8sat obd=up rpm=850 spd=0 buf=127 fast=28 seq=4 pub-ok
                                                                  ~~~~~~~ ~~~~~~~ 신규
```

UART 진단 앱(`tools/utils-uart-app/main.py`)의 `STAT_KEYS` 는
`("up","mqtt","rssi","gps","obd","seq")` **닫힌 목록**이고, `STAT_RE` 가 이 목록을
"다음 키 경계"로도 씁니다. 앱을 안 고치고 펌웨어만 올리면 `buf=`/`fast=` 가 미지의
토큰이라 **앞 필드 값에 통째로 흡수됩니다** — 신규 필드가 안 보이는 정도가 아니라
`obd`/`seq` 등 **기존 표시가 깨집니다.**

```
0단계  UART 앱 STAT_KEYS 에 "buf","fast" 추가 → 배포        ← 선결 조건
1단계  이 펌웨어 OTA (백필만 활성, fast_ms=0 기본)
2단계  서버 고빈도 경로 배포 → config_update {"fast_ms":1000}  ← OTA 불필요
```

UART 앱은 하위호환입니다(구 펌웨어에 `buf=` 가 없어도 정상 동작) — 그래서 앱을 먼저
올려도 안전합니다. 반대 순서만 위험합니다.

## 무엇이 바뀌었나

### 1. 오프라인 telemetry 적재·백필 — **서버 변경 없음**

지하주차장·터널·기지국 장애 구간의 telemetry 가 지금까지는 그냥 사라졌습니다.
이제 단말 플래시에 적재해 두었다가 재접속 후 올립니다.

| 항목 | 값 |
|---|---|
| 보관 용량 | `spiffs` 파티션 **128KB 를 raw 링버퍼로 전용** — 56B × **2,336건** |
| 적재 주기 | 주행 중 **30초** / 정차·주차 중 **120초** |
| 보관 시간 | 주행 **19.5시간** / 주차 **77.9시간(3.2일)** |
| 폐기 정책 | 링이 차면 가장 오래된 **섹터(73건) 단위**로 폐기 + 폐기 로그 |
| 배출 속도 | 틱당 1건·최소 1초 간격 → 풀 링 배출 **약 45분** |
| 시각 정확도 | `(epoch, millis)` base 유지 → 소스가 끊긴 구간은 millis 외삽(**하루 ±1.7초**) |

**서버는 그대로입니다.** 백필은 기존 `telemetry` 토픽·스키마로 나가고 `ts` 만 과거이며
`sys.bf=1` 이 붙습니다. 서버가 이미 이걸 흡수합니다:

| 우려 | 현재 서버 상태 |
|---|---|
| 과거 시각 중복 | `telemetry` PK `(device_id, ts)` + `ON CONFLICT DO NOTHING` |
| 순서 역전 | `vehicle_state` UPSERT 가 `WHERE vehicle_state.ts < EXCLUDED.ts` — 백필이 현재 상태를 과거로 되돌리지 않는다 |
| 파티션 착지 | `telemetry_default` DEFAULT 파티션 존재. 링 상한이 최대 3.2일이라 현행 범위를 벗어나지도 않는다 |

**실시간 발행이 절대 우선입니다.** 백필은 ① 접속 후 15초 지연 ② 틱당 1건, 최소 1초 간격
③ 다음 실시간 발행 2초 전 금지 — 3중 가드를 통과할 때만 나갑니다. 모뎀은 publish 를
1건씩만 처리하고 겹치면 세션이 깨지기 때문입니다.

### 2. 고빈도(1Hz) OBD 샘플 스트림 — **기본 꺼짐**

30초 주기 telemetry 는 순간값 스냅샷이라 그 사이의 가속·제동·공회전이 전부 사라집니다.
차속(0x0D)·회전수(0x0C)·스로틀(0x11)만 **초당 1회** 모아 창 단위로 1건 발행합니다.

- 토픽 **`v1/{device_id}/telemetry/fast`** (QoS 1), 발행 주기는 telemetry 와 동일(30초)
- 페이로드 ≈ 545B(n=30) — 주행 1시간당 약 85KB, 하루 2시간 기준 **월 약 5MB**
- **이벤트 판정은 서버가** 1Hz 원본으로 합니다 → **임계값 튜닝에 OTA 가 불필요**합니다
- GPS 는 제외했습니다 — 모뎀 AT 왕복이 병목이라, 별도 버스인 CAN(TWAI)만 씁니다
- 시동 OFF → CAN 잠김 → 수집·발행 없음(데이터량 절약)

> ⚠️ **런타임 기본값이 `fast_ms=0`(비활성)입니다.** 서버에 EMQX Rule
> `v1/+/telemetry/fast` 와 `/ingest/telemetry/fast` 가 없으면 발행이 브로커에서 조용히
> 버려집니다(무해하나 데이터·전력 낭비). 서버 준비 후 아래 명령으로 켭니다.

```json
{ "command_id": "...", "type": "config_update", "payload": { "fast_ms": 1000 } }
```

되돌릴 때는 `"fast_ms": 0` — **OTA 없이 즉시 차단**됩니다(롤아웃 안전판).

### 3. 오프라인 창 집계 — 음영 구간의 운전 행태

오프라인에는 1Hz 원본을 남기지 않습니다(2,336건이 1Hz 면 **39분**에 소진). 대신 창마다
집계한 **8바이트**를 오프라인 레코드에 실어 백필 telemetry 의 `agg` 로 보냅니다.

```json
"agg": { "w":30, "n":29, "spd_max":88, "spd_min":54, "rpm_max":2400,
         "accel":2.1, "decel":-3.4, "ev":3, "ev_n":2 }
```

- `w` = 창 길이(초, 주행 30 / 정차 120) — 서버가 이벤트 `duration_s` 를 채우는 데 필요합니다.
  레코드에는 `flags` b4 **1비트**로 저장하므로 추가 바이트가 없습니다.
- `ev` 비트 — b0 급가속 b1 급감속 b2 과속 b3 공회전
- **창에 샘플이 하나도 없으면 `agg` 를 통째로 생략합니다.** 0 으로 채워 보내면 서버가
  "정지·무회전"을 관측값으로 오인합니다.

> ⚠️ 오프라인 판정은 단말이 `config.h` 상수(3.0 / -3.5 m/s² 등)로 합니다. 서버의
> `event_rules` 와 어긋날 수 있으므로 **서버는 `source='agg'` 로 구분해 저장**해야 하고,
> 임계값을 바꿔도 `agg` 유래 이벤트는 **소급 재계산되지 않습니다**(원본이 없습니다).

### 4. 시각 기준(`Clk`) 신설

권위 시각을 얻을 때마다 `(epoch, millis())` 쌍을 base 로 기억하고, 소스가 끊긴 구간은
millis 외삽으로 답합니다. GPS 폴과 telemetry 발행 양쪽에서 갱신됩니다.

**기존 `publishTelemetry()` 의 ts 산출 로직은 건드리지 않았습니다** — 0.2.11 에서 어렵게
확보한 동작이라, epoch 를 얻은 지점에서 `Clk::note()` 만 추가로 부릅니다.
실시간 telemetry 의 ts 는 지금까지와 동일하게 나갑니다.

시각을 한 번도 못 얻은 채 적재한 레코드(`ts=0`)는 업로드 시점에 소급 계산합니다.
같은 부팅 세션이 아니면 복원이 불가해 **폐기**합니다 — `ts=0` 으로 보내면 서버 PK
`(device_id, 0)` 에 여러 건이 한 행으로 붕괴하기 때문입니다(0.2.10 에서 겪은 실패).

### 5. 콘솔·상태 표시

| 명령 | 동작 |
|---|---|
| `buf` | 미전송 건수 / 링 크기 / 누적 적재·업로드·폐기 / head·tail·커서 / 시각 기준 |
| `buf clear` | ⚠️ 링 전체 erase — **미전송 주행 데이터가 사라집니다**(현장 초기화용) |
| `fast` | 현재 창 샘플 수 / 누산 중 집계 / 마지막 배출 집계 / 누적 발행·생략 / 폴 상태 |

신규 로그 태그 **`[BUF]`**, **`[FAST]`**.

## ⚠️ `spiffs` 파티션을 전용합니다

`spiffs` 파티션(0x3D0000, 128KB)을 **SPIFFS 로 마운트하지 않고** `esp_partition_*` 로
raw 링버퍼로 씁니다.

- SPIFFS 는 128KB 에서 메타데이터·GC 로 실사용이 ~100KB 로 줄고 GC 가 수백 ms 스톨을 냅니다.
- 차량 상시전원은 크랭킹·브라운아웃으로 **쓰기 도중 전원이 끊깁니다.** SPIFFS 는 이때
  파일시스템 전체가 손상돼 마운트 실패로 갈 수 있으나, raw 링은 손상 섹터 하나만 버리면 됩니다.
- 이 펌웨어는 SPIFFS/LittleFS 를 전혀 호출하지 않습니다(영속화는 전부 `Preferences`=NVS).

→ **이후 파일시스템이 필요해지면 이 파티션과 충돌합니다.** 파티션 표 재설계와 함께
다뤄야 합니다.

**용량을 늘리려면 USB 재작업이 필요합니다.** OTA 는 `app0`/`app1` 슬롯만 기록하고
파티션 표(0x8000)는 부트로더가 읽는 별도 영역이라, **현장 단말에서 확보 가능한 공간은
현재 파티션 표가 정한 128KB 가 상한**입니다. 그래도 섹터 수를 컴파일 상수로 박지 않고
`part->size` 에서 매 부팅 계산하므로, 차후 파티션을 재설계해도 **같은 펌웨어가 두 종류
단말을 모두 지원**합니다.

## 배포 절차

1. `keyplus-diagnostic-0.2.12.bin`을 HTTP(S)로 접근 가능한 곳에 올린다.
2. `ota-manifest.json`의 `url`을 실제 주소로 채워 배포 기록으로 남긴다.
3. `ota_start.json`의 `command_id`(UUID)와 `url`을 채운다.
4. 대상 단말의 **`v1/{device_id}/cmd`** 토픽으로 발행한다 (QoS 1).
5. 단말이 다운로드 → 플래시 → 재부팅한다.
6. 재부팅 후 MQTT 재접속되면 **`v1/{device_id}/cmd/ack`** 로 결과가 올라온다.

## ⚠️ 반드시 지킬 제약

### 1. 명령 JSON은 **약 1,000 바이트 미만**이어야 한다

래퍼(`TinyGsmMqttA76xx`)가 토픽과 페이로드를 **하나의 버퍼에** 나눠 담기 때문에,
토픽 길이만큼 페이로드 여유가 줄어듭니다(1024B − 토픽 24B ≈ 1,000B). 넘치면
**경고 없이 잘리고**, 잘린 JSON은 `url`이 빈 값이 되어 `[OTA] 잘못된 URL`로 실패합니다.

```bash
python3 -c "import json;print(len(json.dumps(json.load(open('ota_start.json')),separators=(',',':'))),'bytes')"
```

### 2. `version`은 `0.2.12`와 **정확히** 일치해야 한다

재부팅 후 실행 이미지의 `FW_VERSION`과 대조해 ack를 결정합니다(`ota.cpp`).
불일치하면 실제로는 성공했어도 **`failed`로 ack**가 나갑니다.

### 3. URL은 `http`로 시작해야 한다

`ota.cpp`가 `url.startsWith("http")`로 1차 검증합니다. HTTPS 권장.

### 4. 다운로드 중에는 MQTT가 끊긴다

모뎀의 SSL 컨텍스트를 HTTP(S)에 양보하려고 `Mqtt::stopService()`를 먼저 호출합니다.
그래서 ack는 재부팅 후 재접속 시점에 발행됩니다(NVS pending).
**세션이 없으므로 백필·고빈도도 자동으로 멈춥니다** — 백로그는 재부팅 후 유지됩니다.

### 5. 재부팅 후 10분 안에 MQTT에 붙어야 확정된다

새 이미지는 `PENDING_VERIFY` 상태로 부팅하고, MQTT 접속에 성공해야
`Ota::onHealthy()`가 확정(`mark_valid`)합니다. `OTA_CONFIRM_DEADLINE_MS`(10분) 안에
못 붙으면 **자동 롤백 재부팅**됩니다.

→ 전파가 약한 곳이나 **전원이 불안정한 차량에서는 OTA를 피하세요.**

### 6. 첫 부팅에서 링버퍼가 초기화된다

`spiffs` 파티션에 유효한 링 헤더가 없으면 섹터 0을 erase 하고 `sector_seq=1` 로
시작합니다. 부팅 로그에 다음이 남아야 정상입니다.

```
[BUF] 유효 섹터 없음 — 링 초기화 (32섹터 / 2336건)
[BUF] 링 준비됨 — 32섹터 2336건 수용, 미전송 0건 (boot=1)
```

`[BUF] 파티션 'spiffs' 없음` 이 나오면 파티션 표가 `min_spiffs.csv` 가 아닌 것입니다 —
오프라인 적재만 비활성되고 나머지 기능은 정상 동작합니다.
